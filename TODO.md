## Publisher list review follow-ups

None of the items below are live bugs — the publisher list works correctly as shipped. A _live bug_ means some input or interaction the app can produce today yields wrong behaviour. The rest are latent hazards: code with a precondition it does not enforce, where nothing currently violates that precondition. Ordered by what is worth doing first.

- [x] **No error boundary** — `apps/vite-project/src/App.tsx`. A throw anywhere under `ProclaimerProvider` blanks the whole app with no fallback UI. Wrap the tree in an error boundary.

- [ ] **Thin test coverage** — `packages/proclaimer/tests/index.test.ts` only asserts that exports are functions, which gives a false sense of security. Add real tests: `ProclaimerProvider` renders children, `PublisherList` renders the not-configured/empty/error states, and `usePublishers` maps rows correctly. Note the singleton caveat above before writing these.

- [ ] **`as PublisherRecord[]` assertion still unchecked, and the schema is not wired into the collection** — `packages/proclaimer/src/feature/publishers/publishers-collection.ts`, in `queryFn`. `database.types.ts` is gone and types now derive from `publisher-schema.ts`, but the cast survived the migration and is now _more_ misleading than before: a reader sees a zod schema in the same folder and reasonably assumes rows are validated. Nothing validates them. The Supabase client is also no longer generic (`TypedSupabaseClient = SupabaseClient`), so `.from("publisher").select("*")` returns `any`-ish data and the cast is the only thing giving it a shape — meaning a column rename or an enum value the schema does not list passes straight through to `PublisherListItem` and surfaces as a confusing render-time error rather than at the fetch boundary.

  The fix is to pass `schema` to `queryCollectionOptions` so TanStack DB validates each row, but it does **not** work as a drop-in — verified against `@tanstack/query-db-collection@1.2.1`:
  - `id: z.uuid().optional()` makes `getKey` return `string | undefined`, which fails the `TKey extends string | number` constraint. The schema currently serves double duty as a row shape and an insert shape, and the row shape is the one the collection needs.
  - The explicit `queryCollectionOptions<PublisherRecord>` type argument selects the non-schema overload, so it conflicts with `schema` and must be dropped to let the schema drive inference.

  The combination that type checks cleanly (`vp check` passes, and `use-publishers.ts` needs no change because the type flows through from the schema): make `id` required in `publisherSchema`, derive the insert shape with `publisherInsertSchema = publisherSchema.partial({ id: true })`, rename `PublisherRecord` to `z.infer<typeof publisherSchema>` and export `PublisherInsert` alongside it, then drop the explicit generic, `return data ?? []`, and add `schema: publisherSchema`. This also removes the hand-rolled `Omit<Publisher, "id"> & { id: string }` in favour of the schema being the single source of truth. Do this together with the `createSupabaseClient` validation item below — they are the two halves of "fail loudly at the boundary."

- [ ] **No publisher type is exported from the package entry point** — `packages/proclaimer/src/index.ts`. The `Database` and `PublisherRow` re-exports were removed with `database.types.ts` and nothing replaced them, so `PublisherRecord` is package-internal. Not a live bug: `apps/vite-project` only imports `ProclaimerProvider` and `PublisherList`, and `PublisherList` is self-contained, so no consumer needs the type yet. It bites the moment an app wants to type a variable holding a publisher, write a helper over the list, or render its own row component — the escape hatch is a deep import into `feature/publishers/publisher-schema.js`, which bypasses the entry point and hardens internal paths into consumer code. Add `export type { PublisherRecord, PublisherInsert } from "./feature/publishers/publisher-schema.js";` (and consider exporting `publisherSchema` itself once forms need it for validation).

- [ ] **`TypedSupabaseClient` no longer describes anything typed** — `packages/proclaimer/src/supabase/create-supabase-client.ts`. Now that the `Database` generic is gone, the alias is `SupabaseClient` verbatim, so the name promises schema-aware queries that were deliberately given up. Purely a naming/comprehension hazard — no runtime or type effect — but it is the kind of stale name that leads someone to trust `.from("publisher")` for typo checking it no longer does. Either rename to `SupabaseClient` at the three use sites (`supabase-context.ts`, `publishers-collection.ts`, plus the `index.ts` re-export, which is a breaking change for consumers) or keep the alias for compatibility and comment that it is intentionally untyped.

- [ ] **Schema optionality leaks `undefined` into row types** — `packages/proclaimer/src/feature/publishers/publisher-schema.ts`. Nullable columns are modelled `.nullable().optional()`, so `PublisherRecord["middle_name"]` is `string | null | undefined`. PostgREST returns explicit `null` for a missing value and never omits the key, so the `undefined` arm is unreachable for rows read from the database; it exists only because the same schema also has to accept inserts that omit the field. Harmless today — `publisher-list-item.tsx` uses `??`, which handles both — but it forces every future consumer to handle a third state that cannot occur, and it weakens `exactOptionalPropertyTypes`-style checks. Resolved by the row/insert schema split described above: keep `.nullable()` on the row schema and let `.partial()` introduce optionality only on the insert schema.

- [ ] **No validation in `createSupabaseClient`** — `packages/proclaimer/src/supabase/create-supabase-client.ts` passes whatever it is given straight to `createClient`. Throw a clear error on an empty or malformed URL/key so misconfiguration fails loudly instead of producing cryptic network errors. (The provider already guards the empty case before calling this, so today it is defence in depth.)

- [ ] **`QueryClient` uses library defaults** — `packages/proclaimer/src/providers/proclaimer-provider.tsx`. Defaults refetch on window focus and retry failures fairly aggressively, which may not suit this app. Set explicit `defaultOptions` (`staleTime`, `retry`, `refetchOnWindowFocus`).

- [ ] **`useSupabase()` returns `null` instead of throwing** — `packages/proclaimer/src/providers/supabase-context.ts`. The mildest item on the list. Returning `null` was deliberate so `PublisherList` can render the "set your env vars" state instead of crashing on a blank `.env`, and the single consumer (`usePublishers`) null-checks and propagates `isConfigured`, so nothing is unhandled. The cost is that `null` now means two different things — "no provider above me" (programmer error) and "provider exists but was not configured" (expected state) — and the hook cannot distinguish them, so a component mistakenly rendered outside the provider quietly shows the configure-your-env-vars message instead of throwing. Either document this or split into `useSupabase()` (throws) and `useSupabaseOrNull()`.

- [ ] **Multiple GoTrueClient instances warning** — visible in the dev console. Caused by React StrictMode double-invoking the `useState` initialiser in `ProclaimerProvider`, which constructs two Supabase clients and discards one; not caused by the collection singleton. Confirm it does not appear in a production build, and consider hoisting client creation out of the component if it does.

- [ ] **`.env` is still git-tracked despite `.gitignore` update** — `apps/vite-project/.gitignore` now ignores `.env`, but the file was already tracked before the Supabase credentials were added. Adding a file to `.gitignore` does not untrack it; git continues tracking already-tracked files. The Supabase URL and anon key in `apps/vite-project/.env` will be committed unless the file is first untracked with `git rm --cached apps/vite-project/.env`. The anon key is designed to be public (safe for client-side use), so this is not a credential breach, but it is clearly unintentional given the `.gitignore` change. Untrack before committing to avoid pushing the key into git history.

- [ ] **Inconsistent import file extensions (`.ts` vs `.js`)** — the proclaimer package mixes `.js` and `.ts` extensions in relative imports. With `moduleResolution: nodenext` both work, but the inconsistency is a maintenance hazard. `index.ts` uses `.ts` for `use-publishers` but `.js` for every other export; `use-publishers.ts` uses `.ts` for all three imports; `publisher-list.tsx` uses `.ts` for `use-publishers` but `.js` for `publisher-list-item`. The dominant convention across the rest of the package and the other packages is `.js`. Normalise all relative imports in the proclaimer package to `.js`.

- [ ] **`PublisherList` empty-state co-located with mapped items** — `packages/proclaimer/src/feature/publishers/components/publisher-list/publisher-list.tsx`. The "No publishers found" message is rendered as an `IonItem` inside the same `IonList` as the mapped publishers, guarded only by `publishers.length === 0`. Not a bug today, but if a future search/filter is applied to the list, the empty-state check would need to run against the filtered result, not the raw data — otherwise both filtered-out items and the empty message could render simultaneously. Worth noting if filtering is planned.

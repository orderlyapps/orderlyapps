- [ ] **`useUpdatePublisher` — `onError` callback exceptions are silently swallowed** — In `packages/proclaimer/src/feature/publishers/hooks/use-update-publisher.ts`, the `.catch()` handler calls `onError(toError(reason))` inside a `void`-ed promise. If `onError` itself throws synchronously, the rejection becomes an unhandled promise rejection. Consider wrapping the callback invocation in a try/catch.
- [ ] **`usePublishers` — `error` is `null` when `isError` is `true`** — In `packages/proclaimer/src/feature/publishers/hooks/use-publishers.ts`, `buildPublishersResult` derives `error` from `publishers.utils.lastError`, but `isError` also reflects the `useLiveQuery` error. Consumers fall back to their generic message (e.g. "Failed to load publishers") and the actual error detail is lost. Consider surfacing the `useLiveQuery` error as a fallback when `lastError` is unavailable.
- [ ] **`publisher-details.tsx` uses `describeSupabaseError` instead of `describePublisherError`** — `packages/proclaimer/src/feature/publishers/components/publisher-details/publisher-details.tsx` imports `describeSupabaseError` from `@amodeo/utils/supabase` for load errors, while its child components `NameDetailRow` and `FamilyDetailRow` use `describePublisherError` from `publisher-errors.ts` for update errors. `describePublisherError` delegates to `describeSupabaseError` for non-publisher-specific cases, so using it in the parent would be a strict improvement — it adds publisher-specific messages (e.g. 23503 FK on `family_id` → "The selected family or group no longer exists.") without losing any existing behavior.

## Utils Package — TODO

- [ ] **`@amodeo/utils` main export missing `development` condition** — `packages/utils/package.json` defines `development` and `types@development` conditions for the `./supabase` subpath but not for the main `.` export. This means imports from `@amodeo/utils` (e.g. `toError`, `getErrorMessage`) resolve to built dist during development while `@amodeo/utils/supabase` resolves to source. ## UI/Ionic Package — TODO

- [ ] **`Body` component — `IonicColor` vs Ionic's `Color` type** — `packages/utils/src/vendor/ionic/types/ionic-color.ts` restricts colors to 9 predefined names. Ionic's built-in `Color` also accepts arbitrary custom color names registered in theme CSS. If consumers define custom Ionic colors they will be blocked by this strict type. Additionally, duplicating a vendor type in `@amodeo/utils` means it can drift from future Ionic versions. Consider re-exporting Ionic's `Color` type instead.
- [ ] **`Body` component — `balance` and `pretty` mutual exclusivity** — If both `balance` and `pretty` props are `true`, `balance` silently wins (`body.tsx:59-63`). Consider making the mutual exclusivity explicit at the type level, e.g. a union prop like `wrap?: "balance" | "pretty"`.
- [ ] **Redundant `ref` declaration in input component props** — `TextInputProps`, `EmailInputProps`, `NumberInputProps`, and `SelectInputProps` all re-declare `ref?: Ref<HTMLIonInputElement>` (or `HTMLIonSelectElement`) in an intersection type that already includes it from the layout props. The `ref` is already present in `InputLayoutProps` / `SelectLayoutProps` via `ComponentProps<typeof IonInput/IonSelect>`. The redundancy is harmless but could be cleaned up by removing the explicit `ref` from each input props type.
